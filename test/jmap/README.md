# JMAP test portfolio

WildDuck has no JMAP implementation yet. This directory defines what it will be tested against, so that development starts with the guardrails in place. It holds no test code: the catalogue is the specification the tests are written from, phase by phase.

Build and open `overview.html` (`node test/jmap/tools/build-overview.js`) for the readable version (research summary, phase gates, coverage matrix, findings, and every scenario with a filter).

## Layout

| Path                                  | Content                                                                                                                            |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `catalogue/*.yaml`                    | The scenario catalogue, one file per JMAP area. About 2,500 scenarios                                                              |
| `external/jmapio-expectations.yaml`   | Expected result for each of the 309 tests of jmapio/jmap-test-suite                                                                |
| `external/fastmail-expectations.yaml` | Expected result for each of the 173 files of fastmail/JMAP-TestSuite                                                               |
| `external/README.md`                  | How to run both suites against WildDuck, and how the expectation files work as a gate                                              |
| `tools/check-catalogue.js`            | Validates the catalogue and the expectation files                                                                                  |
| `tools/build-overview.js`             | Renders `overview.html` from the catalogue, the expectation files and `tools/overview-template.html`                               |
| `tools/edit-catalogue.js`             | Edits scenario fields in place without reformatting the YAML (`node test/jmap/tools/edit-catalogue.js edits.json`), then validates |
| `overview.html`                       | Generated by `tools/build-overview.js`, not committed (listed in `.gitignore`)                                                     |

```bash
node test/jmap/tools/check-catalogue.js            # validate every catalogue file
node test/jmap/tools/check-catalogue.js <file>     # validate one file
node test/jmap/tools/build-overview.js             # regenerate overview.html
```

## The five layers

| #   | Layer                                                                                                                                  | Where                                  | Runs                                                    |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------- |
| A   | Backend prerequisites (phase 0): stable ids, journal, state anchor, upload expiry, auth scope                                          | `catalogue/wildduck.yaml`, ids `WDP-*` | In the existing `npm test`, before any JMAP code exists |
| B   | Scenario catalogue: WildDuck's own conformance tests over plain HTTP, many of them seeding or mutating over IMAP, LMTP or the REST API | `catalogue/*.yaml`                     | Every commit, from phase 1                              |
| C   | jmapio/jmap-test-suite, black box, RFC 8620 and 8621                                                                                   | `external/jmapio-expectations.yaml`    | From the end of phase 2 (it seeds through JMAP writes)  |
| D   | fastmail/JMAP-TestSuite, black box, adds Blob, contacts, calendars                                                                     | `external/fastmail-expectations.yaml`  | Nightly, through a WildDuck adapter                     |
| E   | Client interop: jmap-jam, aerc, meli, Ltt.rs, Bulwark Webmail, Twake Mail, Cypht                                                       | `overview.html` section 7              | End of each phase                                       |

In phase 1 only layers A and B can run, so the phase 1 scenarios carry that gate alone.

## Phase gate

A phase is complete when

1. every catalogue scenario with that phase number or lower passes,
2. every external test expected to pass by that phase passes,
3. every external test listed as `never` still fails (an unexpected pass means the list is out of date).

Phases follow the feasibility review: 0 backend prerequisites, 1 core and read only mail, 2 writes, 3 submission, 4 conformance extras, 5 contacts, 6 calendars, 7 calendar scheduling (held until the calendars draft is an RFC).

## Scenario format

```yaml
area: email-get
title: 'Email/get'
description: 'What this file covers.'
scenarios:
    - id: EGET-001 # PREFIX-NNN, permanent, never renumbered or reused
      title: 'Short statement of the behaviour'
      method: Email/get # JMAP method, or a pseudo area such as Session, Request, Upload, EventSource, Auth
      spec: 'RFC 8621 4.2' # where the expectation comes from
      level: must # must | should | may (RFC wording), wd (WildDuck design decision)
      phase: 1 # phase in which the scenario must start passing
      applies: yes # yes | adapted (rewritten for a WildDuck constraint) | no (kept for traceability)
      seed: [imap] # none, jmap, imap, api, lmtp, smtp, db, time
      given: 'State before the call.'
      when: 'The request.'
      then: 'The assertions.'
      sources: # tests in other suites that check the same behaviour, or the RFC section
          - 'james:EmailGetMethodContract#...'
          - 'cyrus:JMAPEmail/email_get_...'
      notes: 'Optional. Open questions, why adapted.'
      planned: false # optional, marks features outside the current plan
```

Source prefixes: `james`, `cyrus`, `stalwart`, `jmapio`, `fastmail`, `tmail`, `legacy-proxy`, `jmap-perl` (a test in that project), `rfc` (derived from the spec text), `wildduck` (derived from WildDuck's design or code).

## Running the scenario tests

```bash
npm run test:jmap            # start a test server, run test/jmap/scenarios, stop the server
npm run test:jmap:coverage   # the same, then check that every scenario of a finished work package passed
npm run test:jmap:catalogue  # validate the catalogue and the expectation files, build overview.html
```

`npm test` and CI run the scenario target too (Grunt `shell:mocha-jmap`), and CI runs the coverage check. Finished work packages and the scenarios they must keep passing are listed in `progress.json`.

The harness lives in `harness/` and is loaded with `require('../harness')`:

| Module             | Gives                                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scenario(id, fn)` | Registers the Mocha test for a catalogue scenario; the title is the id plus the catalogue title. Unknown or duplicate ids fail at load time, withdrawn scenarios are registered as pending        |
| `accounts`         | `createUser`, `mailboxes`, `createAsp`, `createToken`; every user created is deleted after the run                                                                                                |
| `seed`             | `deliver` (LMTP), `imap` and `withImap` (imapflow sessions), `db` (MongoDB of the test server)                                                                                                    |
| `api`              | The REST API of the test server                                                                                                                                                                   |
| `fixtures`         | `buildMessage` (nodemailer MailComposer), `readFixture`, `listFixtures` over WildDuck's own fixture directories                                                                                   |
| `clock`            | `waitFor` for asynchronous effects, `delay`                                                                                                                                                       |
| `outbound`         | The outbound queue of the test server (`entries`, `message`, `lock`, `remove`) and a stand in for ZoneMTA: `deliver` hands a queued message to local recipients over LMTP, optionally DKIM signed |

`hooks.js` (root hooks) closes connections and removes test users; `reporter.js` writes per test results to the file named by `JMAP_RESULTS`.

## Turning scenarios into tests

- Put the scenario id in the test title, for example `it('EGET-012 returns notFound for a \\Deleted message', ...)`, so results can be matched to the catalogue.
- Drive JMAP with a thin helper over `fetch` rather than a typed client library: conformance tests must send malformed requests, check raw HTTP status codes and use Basic auth, which the libraries hide.
- Seed with the mechanism named in `seed`. Cross protocol scenarios (change over IMAP or the REST API, observe over JMAP) are the ones no external suite can run, so do not replace their seeding with JMAP calls.
- When a scenario turns out to be wrong, fix the scenario in the same change as the test. When it is withdrawn, keep the id and set `applies: no` with the reason.
- Scenario notes that start with an assumption ("Assumed ...") mark an open design question. Settle it before writing the test, then update the note.

## Rules for the sources

- Scenarios are written in our own words. Other suites are cited by test name; their code, expected JSON and fixtures are not copied. Stalwart's tests are AGPL, and the two independent suites have no licence file.
- The independent suites are run as external tools at the commit pinned in their expectation file. They are not vendored.
- The jmapio suite contacts the public relay smee.io for its push tests. See `external/README.md` before running it against anything but a throwaway instance.
- Fixtures come from WildDuck's own corpus (`imap-core/test/fixtures`, `test/fixtures`) and from permissively licensed parser corpora.
