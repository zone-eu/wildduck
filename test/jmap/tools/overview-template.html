WildDuck JMAP test portfolio

Built 2026-11-11 on branch jmap-test-portfolio, as the guardrail for the JMAP plan (feasibility review revised 2026-11-11, phases 0 to 7). Generated from test/jmap/catalogue/*.yaml and test/jmap/external/*-expectations.yaml by node test/jmap/tools/build-overview.js. Do not edit this page by hand.

1. Summary

WildDuck has no JMAP code yet. This portfolio defines, before development starts, what "works" will mean at every phase: {{total}} scenarios in a structured catalogue, each tied to an RFC section, to the phase in which it must start passing, and to the tests in other servers that check the same behaviour, plus two independent black box conformance suites with a per test prediction for WildDuck. No test code is written yet, by decision: the catalogue is the specification the tests will be written from.

{{cards}}

How to use it. When a phase starts, its scenarios become Mocha tests (the scenario id goes into the test title). A phase is done when every scenario due by that phase passes and both external suites match their expectation lists. Section 4 has the numbers.

4. Phase gates

A phase is complete when (1) every catalogue scenario with that phase number or lower passes, (2) every external test expected to pass by that phase passes, and (3) every external test listed as never still fails. The third rule makes an unexpected pass visible, so the list is corrected instead of drifting.

{{phases}}

External counts include tests where the suite is stricter than the RFC but WildDuck plans to comply. Phase names follow section 8 of the feasibility review. Phase 7 is held until the calendars draft is published as an RFC.

8. Rules for using the sources

  • Scenarios are written in our own words. The catalogue cites other suites' tests by name and never copies their code, expected JSON or fixtures. This matters most for Stalwart (AGPL) and for the two independent suites, which have no licence file.
  • The independent suites are run, not vendored. CI fetches each at the commit pinned in its expectations file. Updating the pin is a deliberate change that is reviewed together with the expectation list.
  • The jmapio suite contacts a public relay (smee.io) for its push tests. Runs against anything but a throwaway instance should block that or skip the push tests.
  • Fixtures come from WildDuck's own corpus (imap-core/test/fixtures, test/fixtures) and from permissively licensed parser corpora (mailparser, postal-mime, MimeKit under MIT). James's sixteen .eml files are Apache 2.0 and may be used with attribution.
  • A scenario id is permanent. Scenarios are never renumbered; a withdrawn scenario keeps its id with applies: no and a reason.

Decisions taken and defaults chosen

Quota is included (phase 4), Email/queryChanges is general with cached results, VAPID is included, and the pull request covers phases 0 to 6. The remaining items below have defaults in section 1.3 of docs/jmap/implementation-plan.md; each is also recorded in the notes of the scenarios it affects.

  • Quota capability (RFC 9425). Decided: included in phase 4, so the Cypht webmail client can connect (QUOTA-*).
  • Identity before submission. Moot in a single pull request: the submission capability ships with both.
  • Scope of Email/queryChanges in phase 4. The plan sketches mailbox views sorted by receivedAt. A Fastmail test uses a text filter with a subject sort and two jmapio tests use no mailbox filter. Decided: general queryChanges backed by cached query results, so these pass.
  • Text search semantics. MongoDB $text ORs terms, treats a leading minus as negation and mixes headers with body; JMAP wants all terms, and body separate from headers. Stop words and stemming in the phase 4 OpenSearch analyzer must not swallow short terms the suites search for.
  • Safety window on sinceState. It can report an id twice, which the RFC allows, but tests then cannot assert exact lists. Tests need a deterministic mode or set based assertions.
  • Shared state string. Every mail change moves the Email, Mailbox and Thread states together, so ifInState on Mailbox/set trips on unrelated mail delivery (MBX-218), and every push names all three types.
  • Account id format. The plan uses the user id (24 hex, may start with a digit) and also says ids are letter prefixed (CORE-009).
  • maxObjectsInGet. 500 conflicts with 1,500 mailboxes when Mailbox/get is called with ids null (CORE-088).
  • Phase 1 advertises more than it implements. The mail capability and uploadUrl exist before the write methods do. Assumed: unknownMethod and HTTP 501 (CORE-099, BLOB-002).
  • Threading rule. References plus equal subject, the rule the RFC suggests, costs the largest query file of the Fastmail suite, which assumes references only.
  • Subscription default. WildDuck subscribes new mailboxes and the RFC says SHOULD default to true; two Fastmail files expect false.
  • Contacts and calendars. Values for maxAddressBooksPerCard and maxCalendarsPerEvent, card size limits and a contact quota, whether register entries are synthesised on read or stored as cards, the meaning of a null calendar time zone without principals, and whether an inbound CANCEL destroys the event or marks it cancelled.
